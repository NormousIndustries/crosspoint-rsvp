## Preferences, defaults and write policy

| JSON key | Representation | Default | Accepted values |
| --- | --- | --- | --- |
| `rsvpWpm` | Integer WPM | 100 | 50, 75, 100, 125 |
| `rsvpSmartTiming` | Integer toggle | 1 (On) | 0 (Off), 1 (On) |

Missing, negative, fractional, boolean, string, oversized or unsupported values
fall back to 100 WPM / On. Integer 0 is valid only for Smart Timing. A malformed
settings file is rejected by the existing store before deserialization into
settings; a fresh boot retains constructor defaults. Invalid values do not
trigger an automatic migration write for these keys.

Speed controls change only the activity's cadence in RAM. On **RSVP exit**
(Back, normal global navigation or paused auto-sleep), after source handles and
temporary spools are released, `saveRsvpSpeed()` writes the existing settings
document only if the final supported WPM differs from its saved selection.
Reaching a speed limit, an unchanged session, or returning to the original
speed before exit causes no speed-preference write. There is no save per word,
pause, resume, manual step or chapter transition. A failed write logs an error
and restores the previous in-memory preference; progress saving still proceeds.

**Power loss before RSVP exit retains the previously saved speed.** The store's
existing SD write is not transactional: interruption during that write may
leave invalid JSON, in which case boot uses safe defaults. This milestone does
not add a new NVS subsystem or change that existing whole-document policy.

Access: **Home → Settings → Reader → RSVP Smart Timing**, select the row and
press Confirm to toggle Off/On. It is a genuine reading preference, shown only
on the X3. Each deliberate toggle uses the existing immediate settings save.
The existing Settings Back save and shared web settings API are retained.
The toggle appears in that shared API as `rsvpSmartTiming`; speed remains
controlled by the six accepted physical RSVP controls. No setting is added to
System or to the playing screen.

Settings serialization preserves all existing EPUB preferences. RSVP preferences
contain no spine/word position and do not change the reader render specification.
Per-book progress remains in its existing binary `progress.bin` via `ProgressFile`.

On: existing maximum-wins adjustments remain long +100 ms, comma +150 ms,
colon/semicolon +225 ms, sentence +350 ms, paragraph/chapter +500 ms.
Off: every token requests the base interval, retaining punctuation and structural
metadata for context. Base intervals are 1,200 / 800 / 600 / 480 ms at
50 / 75 / 100 / 125 WPM. Display service can still limit delivered speed.

## Position and chapter resilience

Canonical selection remains `(spineIndex, visibleTextOffset)`. The frozen
`render()` commits history only after successful display completion. Context
uses its separate HalFile cursor and never advances playback. Pause selects the
last completed word; resume redisplays that word before timed Next. Manual
Next/Previous retain exact token identity, including repeated words.

Chapter EOF enters bounded loading and then presents the new chapter's first
available token. Empty chapters advance one bounded load at a time until text
or final EOF; there is no catch-up loop. Previous can cross chapter boundaries
only within the existing 32-token history. Forward replay consumes neither the
source cursor nor a staged token. Earlier visited spools remain available for
context until exit, then are removed after both member HalFiles are released.
An entirely empty EPUB settles at paused EOF without a selected token. Final
word replay remains controlled and returns to paused EOF after its interval.

Back returns the selected source offset through the established normal-reader
pagination path (`EpubReaderActivity.cpp:808–855`). The ordinary reader maps
that offset to an approximate page and subsequently stores the page position.
Re-entering RSVP starts at a valid word near that page's visible-text offset;
exact word recovery across a normal-reader round trip is not promised. Power
loss during RSVP retains the previous normal-reader progress; there is no
per-word progress write. The mapping and EPUB rendering implementation are
byte-for-byte preserved by the release contract.

Synthetic tests establish the activity's deterministic boundary behavior;
real EPUB chapter parsing, SD timing and physical chapter transitions still
require the checklist below.

## Lifecycle, memory and logging

The V1A ownership fix remains unchanged: HalFile move assignment destroys its
owned implementation under StorageLock. Member playback/context handles are
released before deleting spools; parser cleanup is RAII. The shared render-task
lock protects activity members and deletion. RSVP creates no private task.

There is no new framebuffer, font asset, chapter cache or ordinary-playback
allocation. The activity reuses its existing 2,048-byte context text buffer,
49-word context window, 201-byte shortening scratch and 32-token history.
Large buffers remain members of the checked activity allocation, not local
stack arrays. New firmware locals are small scalar/variant values.

DWARF measurements from both actual ELFs:

| Object | Accepted V1C.2 | V1C.3 |
| --- | ---: | ---: |
| `RsvpReaderActivity` | 12,520 | 12,520 |
| `RsvpCadence` | 96 | 96 |
| `CrossPointSettings` | 216 | 216 |
| `RsvpEpubSource` | 1,912 | 1,912 |
| `Context` | 2,152 | 2,152 |
| `ContextPlacement` | 364 | 364 |

The new scalars occupy existing padding. A new `SettingInfo` is **132 bytes**
in the existing settings vector and its temporary copies. Reusing that existing
descriptor/persistence architecture avoids a separate menu/storage subsystem;
this is justified bounded settings-time heap storage. JSON and serialized-string
allocations already used by the store now include two additional small fields.
They run at boot/settings changes/changed-speed exit, after parser release,
never in ordinary playback. Settings-screen vectors can also hold one additional
row. No runtime heap saving is claimed; unchanged object/linker sizes do not
prove unchanged peak heap consumption.

Retained logs: ENTER/EXIT, PREF load/save/fail, chapter load/ready, source/file
errors, context fallback, SUMMARY, SMART and VISUAL_SUMMARY. Entry now reports
largest internal block; chapter-ready reports heap/system minimum/largest block.
Session minimum heap/block samples continue at load ticks and completed frames.
Context logs remain pause/navigation-only. SMART records the enabled flag and
optional additional time; when Off, additional time is zero while source
classification counts remain available. There is no per-word serial spam.

Progressive heap degradation cannot be measured by mocked heap values in an
emulator. During physical testing, retain serial entry/chapter/context/exit
metrics and compare repeated warmed-up sessions at the same lifecycle point.
Exit metrics precede destruction of the activity itself. System minimum is a
boot-wide low-water mark, not a leak measurement.
