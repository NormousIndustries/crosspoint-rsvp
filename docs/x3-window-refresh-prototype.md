# X3 window-refresh prototype: manual hardware handoff

**Conditional GO for one supervised region transition.** Compilation establishes
that the path is buildable; it does not establish addressing correctness on glass,
reduced BUSY duration, optical transition time, or 500 WPM. Stop after the first
transition and inspect before taking another step. No timed window playback or
10/25/100-transition batches are implemented.

## Files and API architecture

Application calls follow:

`X3WindowTestActivity -> HalDisplay -> FreeInkDisplay -> selected X3 PanelDriver -> EpdBus`

Application code never calls EpdBus. `displayWindow()` is unchanged. The separate
`displayWindowFastExperimental()` returns an explicit result and never substitutes
a full-frame refresh. Only the manual test calls it; ordinary CrossPoint rendering
does not. The facade rejects other panels, inverted output, pending async work,
lent/unavailable framebuffer storage, grayscale uploads, and invalid geometry.
Drivers additionally require powered, idle, synchronized B/W controller RAM with
no pending recovery, boot cleanup budget, or grayscale state.

Changed reader files:

- `lib/hal/HalDisplay.h`, `.cpp`: measured blocking calls and experimental HAL API.
- `lib/GfxRenderer/GfxRenderer.h`, `.cpp`: expose the existing orientation and byte
  alignment conversion through `getAlignedDisplayRect()`.
- `src/activities/util/RsvpDisplayTestActivity.h`, `.cpp`: buffer full-frame stage
  measurements and print them after pause/completion.
- `src/activities/util/X3WindowTestActivity.h`, `.cpp`: new single-step test.
- `src/activities/settings/SettingsActivity.h`, `.cpp`: X3-only settings entry.
- `lib/I18n/translations/english.yaml`: test labels, with normal English fallback.
- This handoff document and the v0.1A test guide's instrumentation note.

Changed SDK files under `freeink-sdk/libs/display/FreeInkDisplay/`:

- `include/DisplayMeasurement.h`: caller-owned timing record, memory rectangle,
  and result enum.
- `include/FreeInkDisplay.h`, `src/FreeInkDisplay.cpp`: opt-in APIs and validation.
- `src/driver/PanelDriver.h`: default `Unsupported` implementation.
- `src/driver/Uc8253X3Driver.h`, `.cpp` and `Uc8279Driver.h`, `.cpp`: bounded FAST
  sequences, recovery guards, and effective-mode observations.
- `src/bus/EpdBus.h`, `.cpp`: timing capture, wait status, nine-byte PTL helper,
  and row-strided region streaming.
- `test/host/run_uc8253_power.py`, `run_uc8279.py`, `run_pro.py`, and
  `pro_stubs/EpdBus.h`: keep the existing host harnesses compatible with the new
  optional bus methods/header. These mocks do not validate the new hardware path.

The SDK changes are **uncommitted inside a Git submodule**. Copying only the
parent repository diff or unchanged SDK SHA will not preserve them. The prototype
archive includes changed reader and SDK source files plus separate patch files.
Generated translation tables are regenerated by the build and are not source edits.

## Measurement definitions

The original RSVP test still uses full-frame stock FAST submissions. Its 99
samples now include `PANEL` and `WAVE` records, while existing start-to-start,
completion-to-completion, delivered WPM, and missed-deadline calculations remain.
Requested FAST that was promoted is marked `fast=0`; a warm FAST comparison should
have `fast=1`, `refreshes=1`, and 52,272 NEW plus 52,272 OLD bytes.

Captured SDK BUSY-wait messages are suppressed while measurements are active.
Their original logging remains for unmeasured normal calls. The new measured
baseline therefore differs from older v0.1A captures in serial logging overhead:
compare A/B/C collected with this firmware, rather than assuming old timing is
directly equivalent. No large log dump occurs during a measured refresh.

All timestamps are monotonic microseconds since boot. Durations are microseconds:

| Field | Meaning |
| --- | --- |
| `call_us`, `total_us` | HAL call start and elapsed blocking call time |
| `NEW_bytes`, `OLD_bytes` | Bytes streamed to NEW/OLD RAM; cleanup may upload more than once |
| `NEW_us`, `OLD_us` | Plane command and transfer time, accumulated across that call |
| `DRF_us` | Timestamp immediately before the first DRF command |
| `BUSY_observed_us` | Task observation of asserted LOW during the existing assertion grace |
| `BUSY_complete_us` | Software return from the first wait after DRF; also populated on failure |
| `DRF_to_complete_us` | DRF through software wait return, including assertion latency |
| `LOW_to_complete_us` | Observed LOW through wait return; available when LOW was observed |
| `wait_us` | Accumulated completion/power/recovery wait time; separate from total call time |
| `setup_other_us` | Total minus NEW, OLD, and waits; includes LUT/PTL/CDI, assertion polling, restore, and wrapper overhead |
| `timeout`, `assertion_missing` | Invalid timing/refresh indicators; exclude such records from comparisons |

LOW observation is task-sampled, not an ISR timestamp or an oscilloscope reading.
Completion includes task wake and bookkeeping. The 50 ms assertion grace and all
existing completion timeout/wait paths are retained. Multi-refresh full cleanups
report accumulated transfers/waits, with timestamps for the first DRF only: do
not use cleanup records as warm FAST waveform comparisons. Rejected calls may
have no DRF or payload, and error logging is included in their HAL duration.

The manual test reports controller/VER, selected geometry, requested screen rect,
actual aligned memory rect, gate bounds, row stride, refresh count/mode, result,
cleanup count, successful manual transition count, and internal 8-bit heap/free
block/boot minimum after every completed action. Manual button intervals are
human-paced and do not define WPM or deadlines. No WPM is calculated for them.

## Region sequence and resources

The default C window is centered within runtime landscape viewable dimensions,
capped at 704 by 160 pixels using theme margins. The renderer's existing conversion
rounds memory X outward to bytes. A requested 704-pixel width can become 712 when
its start is not byte aligned; the logged aligned rectangle is authoritative.
The memory row stride remains the full panel's 99 bytes. Rows are streamed bottom
first, selecting only `width/8` bytes at `x/8` from each source row.

The PTL gate range is `heightPanel - (y + height)` through `heightPanel - 1 - y`,
inclusive. Both drivers preserve the existing X3 nine-byte PTL payload and its
final `01` byte.

UC8253 sequence: PTIN -> bounded PTL -> stock FAST CDI `29,07` and FAST LUT ->
region NEW -> DRF -> unchanged assertion grace/completion wait -> region OLD ->
data stop -> PTOUT -> full visible PTL.

UC8279 sequence: PTIN -> bounded PTL -> region NEW -> data stop -> stock later CDI
and DU bank -> DRF -> unchanged assertion grace/completion wait -> later CDI ->
region OLD -> data stop -> PTOUT -> full visible PTL. OLD stays inside the same
PTL as NEW. The full visible PTL is explicitly restored before a successful return;
PTOUT alone is not used as the restore.

No new framebuffer, region baseline, task, or per-transition allocation exists.
DTM1 retains the OLD image. Callers must alter only pixels inside the submitted
rectangle and hold exclusive display ownership; the manual test holds RenderLock.
No extra host baseline exists to detect unrelated exterior framebuffer changes.

Target ELF type sizes: `DisplayMeasurement` 64 bytes; manual activity 264 bytes;
instrumented RSVP activity 11,608 bytes. The 99 inline measurement additions use
6,336 bytes plus the activity's reusable 64-byte record. Inline activity storage
outlives the render call and is released on activity destruction; stack/static
sample arrays would respectively violate the stack limit or retain RAM after exit.
The manual activity uses one checked `makeUniqueNoThrow` allocation, following
existing activity ownership. Settings reserves one additional action slot before
appending. The measurement methods and region streamer allocate nothing.

## Safety and failure behavior

LUT bytes, drive voltages, CDI values, temperature assumptions, PLL, and configured
10 MHz SPI are unchanged. The experiment is monochrome, non-inverted and blocking.
No electrical/waveform engineering, EPUB integration, ORP, new fonts, registration
markers, Smart Timing, production RSVP UI, or asynchronous refresh is included.

On failed refresh, no experimental OLD synchronization is issued. The driver
invalidates the baseline and requests full recovery. If idle, it restores full
PTL immediately; if BUSY remains asserted, restore is deferred rather than sending
commands while the panel is busy. A later normal full-frame call waits normally
before the deferred restoration. The test blocks further steps until explicit
Left/full cleanup; geometry selection also performs full cleanup. A failed cleanup
does not re-enable steps. Ordinary X3 completion failures also avoid OLD writes
and invalidate baseline state. If BUSY remains stuck, stop and use normal reset/
recovery; do not repeatedly request cleanup.

Result values: `0 Success`, `1 Unsupported`, `2 InvalidState`,
`3 InvalidRectangle`, `4 BusyTimeout`, `5 BusyNotObserved`. No error silently turns
into full-frame FAST. The deliberately selected A comparison is an explicit normal
full-frame call, not a fallback.

## Exact flashing and log capture

Run from `C:\ai\Crosspoint-RSVP\crosspoint-rsvp`. Connect the charged X3 with a
USB data cable and close any monitor first. Reconfirm the USB port; COM5 was the
ESP32 USB port listed in this session, not a guarantee for the next connection.

```powershell
$env:PYTHONUTF8 = '1'
$env:PYTHONIOENCODING = 'utf-8'
$pioPython = "$env:USERPROFILE\.platformio\penv\Scripts\python.exe"
& $pioPython -m platformio device list
$readerPort = 'COM5' # Use the confirmed X3 USB serial port.
$esptoolScript = "$env:USERPROFILE\.platformio\packages\tool-esptoolpy\esptool.py"
& $pioPython $esptoolScript --chip esp32c3 --port $readerPort --baud 921600 write-flash `
    0x10000 build/x3-window/prototype/firmware.bin
& $pioPython -m platformio device monitor --port $readerPort --baud 115200 2>&1 |
    Tee-Object -FilePath build/x3-window/manual-serial.txt
```

The installed esptool 5.3.0 accepts this command; its `.py` entry point emits a
deprecation notice. The app belongs at **0x10000**. A factory image belongs at
**0x0000**, never at the app offset. App-only flashing retains the current
bootloader/partition layout. Normal source-based upload remains:
`& $pioPython -m platformio run -e default -t upload --upload-port $readerPort`.
If connection fails, use the unit's known-good download-mode procedure and retry;
this session has not established a new button sequence. Do not erase all flash.
Exit the monitor with Ctrl+C before flashing again.

## Exact manual hardware procedure

1. Capture startup `[XTDET]` VER and selected controller. Disable dark mode.
   Open **Settings -> System -> X3 window test**. It starts in C, paused without
   a scheduler, and performs one unmeasured-for-comparison full clean. Confirm
   `Morning` near the upper-left of the central test rectangle and stable header,
   footer, and button hints. Inspect `job=full-clean`, `status=0`, `baseline_valid=1`.
2. Press **Confirm once**. Wait for the display and serial report to finish.
   The new `view.` should appear toward the lower-right. Inspect the location,
   row order, cleared `Morning`, absence of wrapped data, contrast, and unchanged
   exterior. Require `job=manual-step`, `status=0`, `fast=1`, `refreshes=1`,
   `timeout=0`, `assertion_missing=0`. NEW and OLD must each equal
   `(aligned_memory.width / 8) * aligned_memory.height`, not 52,272.
3. **Stop and inspect now.** On any misplaced rectangle, reversed rows, uncleared
   old word, exterior change, abnormal BUSY, timeout, ghosting, contrast loss, or
   unexpected full-panel flash, stop further experiments. Save logs/video. Left
   permits a full cleanup only when safe; persistent BUSY requires normal recovery.
4. Press **Back**. Check ordinary Settings rendering and restoration of the prior
   orientation. Exit settings and confirm a normal full-screen/home redraw. Any
   addressing/baseline issue is NO-GO for further window work.
5. Only after this one-step proof is physically correct, re-enter and press
   Confirm individually to alternate A/B words in C. Wait and inspect between
   presses. Right changes comparison geometry **C -> A -> B -> C** and performs
   a full clean with `Morning` before any measured step. A submits full-frame FAST;
   B uses the full native width at the same narrow height; C reduces width too.
   Perform one or a few supervised manual steps per mode, with the same USB,
   charging, temperature, and panel conditions. Left resets the current mode with
   full cleanup. Up/Down have no action in this manual test.
6. Compare only `manual-step` successful warm FAST records. Full-frame A expects
   52,272 bytes per plane; 792 x 160 B expects 15,840; aligned 704 x 160 C expects
   14,080 (712 x 160 expects 14,240). Compare NEW/OLD transfers separately from
   `DRF_to_complete_us`, `LOW_to_complete_us`, and `total_us`.
7. Film the screen at a known frame rate if possible. Compare command/BUSY data
   with the time until the old word clears and the new word is visually stable.
   Reduced payload with unchanged BUSY establishes transfer savings only. Reduced
   BUSY still needs optical evidence. Manual human-paced intervals prove no WPM.
8. Re-enter/exit briefly and check heap/largest block stability; preserve at least
   50 KB free internal heap during tests. The boot minimum includes earlier work.
   Watch Serial for crashes. Do not start timed window testing or long batches.

To collect the instrumented full-frame RSVP baseline, the original **RSVP display
test** entry remains available. First use A's manual one-step measurements for the
same patterns; no 100-word run is necessary to answer the first window question.
If separately collecting v0.1A timing, pause after a short run and read its added
`PANEL`/`WAVE` rows. Full-frame timing still does not verify optical completion.

## Rollback and decision boundary

Close the monitor and restore the pre-edit app binary, without rebuilding:

```powershell
& $pioPython $esptoolScript --chip esp32c3 --port $readerPort --baud 921600 write-flash `
    0x10000 build/x3-window/known-good/firmware.bin
```

Reboot and confirm the known-good RSVP v0.1A behavior/settings. If the bootloader
or partition table also needs recovery, use the archived factory binary at
`0x0000` with the same esptool command, replacing the offset and filename.
Keep the archived source ZIPs and prototype source changes. For source rollback,
extract the two known-good source ZIPs into a separate checkout/location rather
than discarding current work; place the SDK snapshot at `freeink-sdk`.

Unknowns remain: actual controller identity on this unit; physical PTL effects
under the unchanged monochrome FAST waveform; gate-scan/BUSY scaling with height;
clearing/exterior stability and repeated-update ghosting; optical settling versus
BUSY; runtime heap on hardware; successful hardware flash/recovery. No speedup is
claimed from compilation or theoretical wire time.

**GO is limited to supervised physical region-addressing proof.** Further work is
NO-GO on addressing/baseline errors or panel artifacts. The next question remains:
does the logged approximately 704 x 160 memory window materially reduce BUSY **and
optical** transition time relative to A? Timed RSVP/application work waits for
that evidence.
